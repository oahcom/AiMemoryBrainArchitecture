# RFC-IDE-001 — Idempotency Identity Tuple Contract

- Contract ID: RFC-IDE-001
- Version: 1.0.0
- Status: PROPOSED. Core semantics are DECIDED proposals pending review; retention and operational parameters remain CANDIDATE / TO_VALIDATE.
- Counterpart: reviews/contracts/RFC-IDE-001-idempotency-identity-tuple.zh-CN.md
- Consumers: Event Store, SQLite Event Store Adapter, Receipt persistence/recovery, future idempotent write APIs.
- Authority boundary: defines logical identity and replay semantics; does not select a physical database, transaction topology, schema, encryption, or production retention policy.

## 1. Purpose

Define exactly when an append request is a retry of an earlier request. The contract prevents accidental deduplication across producers or authorization scopes, and prevents a reused key with changed content from being reported as success.

## 2. Typed inputs

An idempotent append uses three independent values:

1. **Producer Identity — who initiates the operation.** A stable, authenticated, typed identity for the logical producer principal that owns the retry namespace. It is not a display name, process ID, connection ID, user-supplied label, or partial collection of matching fields. If the producer model distinguishes a principal from a producer installation/instance, the owning identity contract MUST define the exact type and composition; implementations MUST NOT guess whether instance identity participates.
2. **Scope — the authorization boundary.** A typed, canonical scope reference under which the producer is authorized to append and within which the operation and its receipt may be observed. Scope is not inferred from the key and is not a substitute for authorization. Authorization MUST be checked for every request, including retries, before a receipt is disclosed.
3. **Idempotency Key — the caller-selected retry handle.** An opaque, non-empty, bounded value generated by the producer. It is meaningful only inside the namespace below; it is not globally unique and carries no authority.

Digest is the cryptographic digest of the canonical request payload covered by the idempotency contract. It is compared in addition to, not instead of, the identity tuple. Canonicalization and digest algorithm/version must be fixed by the Event Store payload-integrity contract; this RFC does not choose them.

## 3. Identity namespace and replay predicate

**DECIDED proposal — exact namespace:**

    IdempotencyNamespace = (ProducerIdentity, Scope, IdempotencyKey)

The tuple is typed, but the Scope identity/equality domain is **CANDIDATE / TO_VALIDATE** and is not yet normative. The authoritative Scope fields (including whether `scope_id`, `scope_kind`, and/or `namespace_key` participate), namespace/authority qualification, canonicalization and normalization rules, and compatibility/legacy behavior MUST be decided jointly by B/domain and I/security Owners before exact Scope equality is relied upon. Until then, implementations MUST NOT infer a comparator from field names or existing helper behavior. Implementations MUST NOT concatenate unescaped strings, compare only a subset of fields, or substitute a display label for a typed identity.

A request is a replay of an earlier accepted request if and only if all of the following hold:
- authenticated ProducerIdentity is exactly equal;
- Scope equality is **CANDIDATE / TO_VALIDATE** pending the authoritative Scope identity and equality rule; it is not yet a normative replay condition.
- IdempotencyKey is exactly equal; and
- incoming Digest is exactly equal to the digest bound to the durable receipt.

The same ProducerIdentity and Digest alone are NOT sufficient: Scope and IdempotencyKey must also match. However, the Scope comparison domain remains **CANDIDATE / TO_VALIDATE**; the replay predicate must not be treated as fully normative until B/domain and I/security Owners decide the Scope identity tuple, authority/namespace qualification, normalization and compatibility rules. A matching namespace with a different Digest is a key conflict, not a replay.

The first successfully committed request wins. Concurrent requests for the same namespace MUST be serialized by an atomic uniqueness/compare-and-set boundary. Exactly one request may create the receipt and append. A concurrent request with the same digest observes the winning receipt; one with a different digest receives a conflict. A failed transaction that did not commit the event and receipt does not reserve the key.

## 4. Scope behavior

**CANDIDATE / TO_VALIDATE — pending authoritative Scope identity decision:** Scope is proposed as part of the idempotency namespace. Whether two Scope references are distinct for this purpose, and therefore whether the same ProducerIdentity and IdempotencyKey form independent operations/receipts, depends on the unresolved Scope identity/equality domain described in §3. Do not rely on cross-Scope replay isolation as a normative comparator rule until B/domain and I/security Owners decide it.

The proposed behavior is namespace separation, not cross-scope authorization; its exact application remains subject to the unresolved Scope identity/equality decision above. The caller must independently authenticate and be authorized in the target Scope. A caller lacking access receives the normal authorization denial; the implementation must not reveal whether a matching key exists in another Scope.

If project policy instead requires a producer-wide key namespace across all Scopes, that alternative requires an explicit superseding decision; it MUST NOT emerge accidentally from a database uniqueness constraint.

## 5. Conflict and error behavior

For an existing, unexpired namespace:

| Incoming request | Required result |
|---|---|
| Same ProducerIdentity + Scope + Key + Digest | Return original Receipt as replay; do not append again |
| Same ProducerIdentity + Scope + Key, different Digest | IDEMPOTENCY_KEY_CONFLICT; do not append or replace Receipt |
| Different ProducerIdentity, same Scope + Key | Independent namespace; no replay relationship |
| Same ProducerIdentity + Key, different Scope | CANDIDATE / TO_VALIDATE — independent namespace and no cross-scope receipt disclosure only after B/domain + I/security decide Scope identity/equality |
| Only partially matching typed ProducerIdentity | Different namespace; no partial-match dedupe |
| Same namespace while original outcome is UNKNOWN | Return/recover same unresolved receipt state; do not start a second append |

Conflict responses SHOULD identify the conflict class without disclosing stored payload or another Scope's receipt. Receipt data is returned only after current authorization succeeds.

## 6. Receipt durability and lifecycle

A Receipt is the durable record binding one namespace to the accepted Digest and append outcome. At minimum it records typed ProducerIdentity, Scope, IdempotencyKey, Digest (including algorithm/version identity), operation/event reference, terminal or explicitly unresolved status, and creation/expiry metadata required by the retention policy. Exact physical schema is owned by the Event Store implementation.

**DECIDED proposal:**
- Event append and initial Receipt reservation/commit MUST be atomic at the Event Store logical commit boundary. No committed event may exist without its matching Receipt, and no successful Receipt may exist without the corresponding committed append.
- Receipt recovery after process restart MUST reproduce the same replay/conflict result; an in-memory cache is never the source of truth.
- A receipt in UNKNOWN/in-progress state is not success and does not permit another append. Recovery reconciles event and receipt before retry admission.
- Replaying a request never refreshes its original creation time or silently extends its retention deadline.

**CANDIDATE — retention policy:** Retain the full Receipt for at least the maximum supported producer retry/replay horizon, plus the required audit and recovery window. The numeric TTL is deployment/policy-specific and is not frozen here.

**CANDIDATE — safe cleanup model:** Do not simply delete an expired Receipt and then treat the same namespace as new: a delayed retry could append a duplicate. Preferred options are (a) retain a compact durable tombstone containing namespace, Digest, and expiry/retired status for the entire key-reuse prohibition period; or (b) require an explicit producer key-generation epoch/namespace rollover, with a proven bound on delayed delivery, before reclaiming the old namespace. Until selected, expired-key behavior is fail-closed (IDEMPOTENCY_KEY_EXPIRED / no append). Receipt metadata may be compacted only where replay safety is preserved.

**TO_VALIDATE:** Whether full receipts, compact tombstones, or epoch-based reclamation best meets storage cost, audit, privacy, and replay-safety requirements. Validate with delayed-message/replay tests, crash recovery, backup/restore, and concurrent expiry-vs-retry tests.

## 7. Boundary examples

1. **Cross-Scope replay — CANDIDATE / TO_VALIDATE:** Producer P submits key K, digest D1 in Scope A. The same P submits K, D1 in Scope B. Whether these references identify distinct namespaces, and therefore whether this is a new append rather than a replay, remains pending the B/domain + I/security Scope identity/equality decision. Scope B must not receive Scope A's Receipt absent the required authorization.
2. **Partially matching Producer Identity:** ProducerIdentity=(tenant=T, principal=P, instance=I1) and (tenant=T, principal=P, instance=I2) are different identities if the owning identity contract declares instance part of the type. Same Scope, Key, and Digest do not deduplicate. If instance is not part of canonical ProducerIdentity, every adapter must use that canonical type consistently.
3. **Digest differs under same namespace:** P + Scope A + Key K first commits D1. A later request with D2 returns IDEMPOTENCY_KEY_CONFLICT; no second event is appended and the original Receipt remains unchanged.
4. **Concurrent same-digest retry:** Two requests race for the same namespace and D1. One commits; the other returns the same Receipt. Exactly one event exists.
5. **Crash / UNKNOWN:** After a crash around commit, the adapter reconciles durable event and Receipt state. It must not infer abort from a missing in-memory receipt or success from a request timeout.

## 8. Decision register

| Topic | Status | Validation |
|---|---|---|
| Typed namespace = ProducerIdentity + Scope + Key | CANDIDATE / TO_VALIDATE (Scope component) | B/domain + I/security decide participating Scope fields, namespace/authority qualification, canonicalization/normalization and compatibility/legacy rules; then validate exact equality |
| Replay requires same namespace and same Digest | CANDIDATE / TO_VALIDATE for Scope equality | Deterministic unit/reference-model tests after the authoritative Scope equality domain is decided |
| Different Digest under same namespace is conflict | DECIDED proposal | Negative tests; assert no second append and immutable Receipt |
| Cross-Scope same key is independent | CANDIDATE / TO_VALIDATE | B/domain + I/security decide when Scope references are distinct; then run two-scope isolation and receipt non-disclosure tests |
| Partial ProducerIdentity matching forbidden | DECIDED proposal | Identity-type matrix and serialization round-trip tests |
| ProducerIdentity composition (principal vs instance) | CANDIDATE | Identity Owner publishes canonical type and authenticated mapping |
| Digest canonicalization and algorithm/version | TO_VALIDATE | Payload-integrity contract; cross-version golden vectors |
| Full Receipt TTL numeric value | CANDIDATE | Establish retry horizon, audit and recovery requirements |
| Tombstone vs epoch reclamation | CANDIDATE | Delayed replay, crash, restore, concurrency and cost experiments |
| Atomic event+Receipt physical implementation | TO_VALIDATE | Real-file SQLite transaction tests; crash/fault injection and restart replay |
| UNKNOWN reconciliation | TO_VALIDATE | Kill-at-each-boundary tests; prove no duplicate append or false success |

A DECIDED proposal here is a normative proposal for review, not an already approved repository-wide decision. It becomes DECIDED only after accountable architecture/domain/security reviewers accept it and the decision record is updated. Rejected items remain CANDIDATE or OPEN.

## 9. Event Store SQLite Adapter integration

The SQLite Adapter MUST implement this RFC as a consumer of the logical contract, not redefine it.

- Contract reference: RFC-IDE-001 v1.0.0
- Canonical reference: RFC-IDE-001 sections 3–6 (namespace, replay predicate, Scope isolation, conflict, Receipt lifecycle).
- Required behavior: durable uniqueness over the exact typed namespace; same-digest replay returns persisted Receipt; digest mismatch conflicts; authorization precedes receipt disclosure; event and Receipt commit atomically; restart recovers the same behavior; cleanup cannot silently reopen a retired key.
- Required tests: same-namespace same-digest replay; same-namespace different-digest conflict; same key across Scopes; distinct/partially matching ProducerIdentity; concurrent first-writer race; crash before/after commit; restart receipt recovery; expiry/cleanup and delayed replay.
- Authority boundary: SQLite mechanics may prove physical atomicity, but do not decide ProducerIdentity composition, Scope authorization, or Receipt retention policy.

Suggested implementation citation: "Implements RFC-IDE-001 v1.0.0, sections 3–6". A later semantic revision requires pinning the exact version and migration/conformance coverage.

## 10. Non-goals and open dependencies

This RFC does not decide event ordering, EventId generation, payload canonicalization, cryptographic digest algorithm, authorization policy internals, cross-Scope data sharing, physical transaction topology beyond logical atomicity, or production retention/legal-hold rules. Those remain owned by their respective contracts and authorities.

## 11. Review and acceptance

Required reviewers: Domain Model / Producer Identity authority, Scope / Security authority, Event Store owner, and Storage implementation owner. Acceptance requires bilingual semantic parity; explicit approval or enumerated exceptions for each DECIDED proposal; closure or explicit retention of CANDIDATE / TO_VALIDATE items with named validation evidence; and consumer acknowledgement from the Event Store SQLite Adapter line.

No implementation or production acceptance is implied by this RFC or its PR.
