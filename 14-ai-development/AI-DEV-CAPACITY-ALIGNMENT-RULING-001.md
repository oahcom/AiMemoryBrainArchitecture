## 2. Diagnosis / 诊断

### 2.1 首要根因：记录义务没有按风险分级，因而没有容量上限 / Primary Cause: Unbounded Record Obligations

现有治理行为将不同风险、不同影响范围、不同可逆程度的变更，放入近似统一的记录生产机制。记录是否产生、记录需要多完整、记录是否必须独立重复表达，未与变更风险建立可执行的比例关系。

因果链：

1. 记录义务没有按风险等级区分。
2. 低风险、可逆、局部变更与高风险、授权敏感、跨系统变更承担相似的记录负担。
3. 记录生产无法随风险降低而自然缩减，也缺少可证明的停止条件。
4. 每一次记录性合规活动都可以继续产生新的文件、修订和引用关系。
5. 记录生产获得持续且不受风险约束的容量需求。
6. 当提交容量有限时，记录性工作可以持续占据提交与审查资源，而产品实现没有相应的强制容量保障。

这解释了为什么记录会吞掉产品：不是因为记录本身没有价值，而是因为记录义务在制度上没有边界，产品实现却被放在较晚阶段，并且没有与记录产出竞争资源时可执行的优先级约束。

1.1 的提交分布是该现象的直接观测；1.2 中 P0 授权类 issue 在提交历史中没有引用，是风险敏感事项与记录产出之间缺少有效执行关联的另一项观测。

### 2.2 第二根因：规范语料分裂产生镜像维护税 / Second Cause: Split Normative Corpus Creates Mirror-Maintenance Tax

根目录章节与 `docs/en` 不是成员集合一致的规范语料。语言配对也不是字节级镜像关系。

因果链：

1. 根目录与英文目录成员集合不同。
2. 不同集合意味着规范内容的覆盖范围、存在状态和维护边界不能通过简单镜像关系推定。
3. en/zh 配对内容又不能依靠字节相等证明同步。
4. 每次规范变化都需要额外判断哪些文件是对应项、哪些是独立项、哪些内容已经偏离。
5. 维护者必须在规范内容本身之外，持续处理跨目录、跨语言的映射与一致性问题。
6. 这种额外维护工作进一步产生记录、差异说明、重复引用及协调性提交。
7. 规范维护由内容治理扩张为镜像关系治理，持续挤占产品与可执行验证的容量。

这不是简单的重复文件问题。1.3 明确显示规范语料成员集合分裂，且只有有限的字节级相同配对。因此，单纯删除重复文件不能解决成员集合与规范权威边界的问题。

### 2.3 第三根因：门禁不能证明失败，裁决只能依赖文档自证 / Third Cause: Gates Cannot Prove Failure

门禁存在负样本，不等于门禁具有拒绝错误输入的能力。门禁必须证明其对已知错误输入产生预期拒绝，而不是只证明某个进程返回了非零状态。

因果链：

1. `repository-hygiene.yml:65-79` 的负样本只断言 `status > 1`。
2. 该断言没有证明被测检查器拒绝了特定的已知错误输入。
3. `document-management.yml:36-46` 又没有使用合并候选的真实目标基。
4. 两道门禁均不能从现有测试结构中建立完整的“错误输入—正确目标基—检查器拒绝—门禁失败”证据链。
5. 门禁绿色不能作为检查器有效性的充分证据。
6. 治理裁决无法可靠依赖自动化执行结果，只能继续依赖文档说明、摘要和人工自证。
7. 为弥补执行证据不足，组织继续生产说明性记录，而不是以可失败的执行验证替代说明性证明。

1.5 的端到端测试尤其重要：仓库已经存在跨越全部 12 个 crate 的可执行验证载体。因此，当前问题不能简单归因于仓库缺乏执行验证的技术基础。问题在于治理裁决仍依据文档与摘要，而没有将可执行反证设为有效裁决证据。

### 2.4 第四根因：Phase 3 退出判据不可执行，导致阶段边界失效 / Fourth Cause: Non-Executable Phase 3 Exit Criterion

Phase 3 的退出判据是对组件文档属性的描述，而不是一个具有明确通过与失败条件的可执行判定。

因果链：

1. 判据要求组件具有有界目的、归属、契约和开放问题。
2. 这些属性可以通过增加说明、补充归属、完善契约文字持续表达。
3. 判据没有规定哪些可执行行为或验证结果必须存在，也没有规定什么观测结果构成失败。
4. 因此，即使产品级运行时尚未启动，Phase 3 的文档条件仍可能持续被满足或被重新描述。
5. Phase 3 不再构成从架构描述转向产品实现的有效退出边界。
6. prototype/implementation 被留在 Phase 5，产品实现缺少与文档完善竞争时的强制阶段约束。
7. 记录和架构描述可以继续扩张，而产品实现仍被制度性延后。

此处的关键不是 Phase 3 的文档属性没有意义，而是文档属性无法单独证明一个系统已经具备进入实现阶段所需的可执行能力。

### 2.5 根因排序与相互强化 / Causal Ordering and Reinforcement

上述根因按对容量流向的解释力排序：

1. **无风险上限的记录义务**：直接形成持续、无界的记录容量需求。
2. **规范语料分裂**：使记录义务进一步承担镜像关系维护成本。
3. **不可失败的门禁**：使记录成为执行证据不足时的替代性证明材料。
4. **不可执行的阶段退出判据**：使记录与架构描述可以长期替代产品实现的阶段性结果。

四者不是互斥解释，而是相互强化的机制。

其中，A1 限制记录负担的产生条件；A2 限制规范维护的对象和权威边界；A3 限制以文档自证替代执行验证；A4 限制以持续完善文档替代实现阶段退出。

本诊断不主张记录数量本身能够证明每一份记录都没有价值，也不主张减少记录数量本身就必然产生产品。它主张的是：现有机制没有证明记录负担与风险成比例，没有证明门禁可以拒绝错误输入，也没有证明产品阶段已经通过可执行条件获得进入实现的资格。

## 3. Rulings A1–A4 / 裁定 A1–A4

以下四条为拟提交采纳的治理裁定。由于本文件状态为 PROPOSED，四条裁定在 Owner 或明确书面授权的治理权威采纳前，不自动构成仓库现行规范的变更。

### A1. 记录义务按风险分级 / Record-Obligation Tiering by Risk

#### Decision

适用于 `14-ai-development` 中的 work item、decision record、evidence、session evidence，以及涉及架构、治理、授权、实现和文档变更的审查角色：记录义务必须按变更风险、影响范围、可逆性和授权敏感程度分级；低风险、局部、可逆变更不得自动继承高风险变更的完整记录负担；授权敏感、跨边界、高影响或不可逆变更不得因记录减负而免除必要证据。此裁定不改变上位规范中明确规定的强制记录义务，也不替代任何授权要求。

#### Rationale

1.1 显示 `14-ai-development` 记录类提交占有明显的提交容量。

1.2 显示 P0 授权类 issue 在提交引用层面没有对应记录。

2.1 的因果链说明，统一记录负担既可能过度消耗低风险变更的容量，也不能自动保证高风险事项获得有效执行。

因此，记录数量不能作为治理质量的替代指标；记录强度必须与风险对应。

#### Alternatives considered and rejected

**替代方案一：所有变更继续使用统一的完整记录要求。**

否决理由：统一要求没有体现风险差异，无法解释低风险变更为何必须承担与高风险变更相同的记录成本，也没有提供记录容量上限。

**替代方案二：全面取消或尽可能删除记录义务。**

否决理由：这会将高风险授权、不可逆变更和跨边界变更与普通局部变更一并减负，破坏必要的可追溯性，且不能解决 P0 授权事项缺少有效执行关联的问题。

**替代方案三：只根据提交数量决定记录等级。**

否决理由：提交数量不是风险本身。小规模变更也可能涉及高风险授权，大规模变更也可能仅是低风险机械调整。

#### Consequences

本裁定采纳后，新发生的变更不得仅因其属于某种文档类型，就自动承担不加区分的完整记录负担。

必须放弃“记录越多就代表治理越充分”的默认评价方式。

必须放弃将所有 work item 的完整文档结构视为与风险无关的普遍最低负担。

同时必须保留高风险变更的必要证据义务，不能把风险分级解释为普遍豁免。

历史记录不因本裁定而自动失效，也不因其记录过多或过少而自动获得追溯性违规结论。

#### Falsifier

在本裁定适用范围内，若对一个完整审查窗口中的全部新变更进行独立风险分级后，发现所有不同风险等级的变更均实际承担相同的强制记录项目，且低风险变更没有任何可观察的记录负担差异，则 A1 关于风险分级能够形成记录义务边界的裁定被证伪。

观测必须覆盖变更风险等级、实际强制记录字段和记录产出；仅有规范文字声明分级，不构成通过证据。

### A2. 单一规范源 / Single Normative Source

#### Decision

适用于架构规范、治理规范、流程规范及其中文和英文表达：每项规范必须具有一个可识别的规范权威来源；其它语言版本、发布副本、导航页和解释性材料不得因内容相似或路径相同而自动取得独立规范权威。此裁定不要求删除现有语言文件，不要求所有语言文件字节相同，也不改变已明确授权的独立规范范围。

#### Rationale

1.3 显示根目录与 `docs/en` 的成员集合不同，169 个 en/zh 配对中只有 1 对字节完全相同，全仓另有 11 个内容重复组。

2.2 说明成员集合分裂和语言内容差异共同产生映射、同步与权威判断成本。

因此，需要统一的是规范权威来源，而不是强制统一所有文件内容或目录结构。

#### Alternatives considered and rejected

**替代方案一：强制所有中英文文件保持字节级相同。**

否决理由：语言文本的语义等价不要求字节相同；该方案也无法解决不同成员集合所造成的规范覆盖范围差异。

**替代方案二：允许根目录与 `docs/en` 各自成为独立规范源。**

否决理由：相同主题可能同时出现不同版本、不同成员和不同规范边界，维护者无法仅凭路径确定哪份内容具有最终权威。

**替代方案三：立即删除所有重复或非镜像文件。**

否决理由：重复组不等于全部文件都是冗余副本，成员集合不同也不等于其中某个目录可以整体删除。删除行为必须依据具体文档的规范身份和依赖关系判定。

#### Consequences

本裁定采纳后，新建立或修改的规范不得仅凭语言目录、文件名或内容相似性获得独立规范权威。

必须放弃以双目录各自维护同一规范权威的默认模式。

必须放弃以字节相等作为跨语言规范一致性的唯一判据。

中文与英文文本可以保持自然语言差异，但必须能够识别其规范来源和对应关系。

既有文件不因成员集合不一致而自动删除，也不因内容重复而自动失去效力；其历史状态按形成时的规范关系理解。

#### Falsifier

在本裁定适用范围内，若连续完整审查窗口内，仍有任何一项新发布或新修订的规范，在没有明确独立授权的情况下，同时被两个不同文件作为相互独立且同等权威的规范来源引用，则 A2 关于单一规范权威来源能够消除双重规范权威的裁定被证伪。

判定依据是文件声明、规范引用及其授权关系，而不是文件字节是否相同。

### A3. 每一道门禁都必须证明自己能够失败 / Every Gate Must Prove It Can Fail

#### Decision

适用于 `.github/workflows/`、`scripts/` 中的治理检查器及其 required status checks：每一道门禁必须具有与其检查目的相匹配的已知错误负样本，并证明检查器在正确的目标基和合并候选上下文中拒绝该负样本；只证明进程返回非零状态、workflow 成功运行或 required context 变绿，不构成门禁有效性的证明。此裁定不要求每个普通单元测试都成为 required check，也不改变授权权威对门禁范围的批准权限。

#### Rationale

1.4 显示 `repository-hygiene.yml:65-79` 的负样本只断言 `status > 1`，`document-management.yml:36-46` 使用 PR base SHA 而非合并候选实际目标基。

1.5 显示仓库已经具有串起全部 12 个 crate 的端到端可执行测试。

2.3 说明门禁无法证明失败时，绿色结果不能支撑治理裁决，文档说明便成为执行证据不足时的替代品。

因此，门禁的最低证明责任必须从“成功执行”转为“对已知错误输入能够按预期拒绝”。

#### Alternatives considered and rejected

**替代方案一：只要求门禁运行成功并产生绿色状态。**

否决理由：成功运行只能证明执行过程结束，不能证明检查器拒绝了错误输入。

**替代方案二：只测试脚本的非零退出码。**

否决理由：任意错误、参数缺失或内部异常均可能产生非零退出码。该结果不能区分预期拒绝与意外失败。

**替代方案三：继续以人工审查文档和摘要作为门禁有效性的主要证明。**

否决理由：人工说明不能替代对真实目标基、合并候选和已知错误输入的端到端验证；仓库已有可执行测试链路，也没有理由将文档自述视为更强的证据。

#### Consequences

本裁定采纳后，没有已知负样本拒绝证据的检查器不得仅凭绿色 required context 被认定为已证明有效。

必须放弃仅凭 `exit code != 0` 宣称负样本测试有效的做法。

必须放弃将 PR base SHA 自动等同于合并候选实际目标基的验证假设。

门禁的有效性证明必须包含输入、目标基、检查器响应及预期失败结果之间的可复核关系。

本裁定不意味着所有历史绿色状态自动失效，也不意味着任何尚未完成负样本证明的门禁已经被正式撤销。

#### Falsifier

在本裁定适用范围内，若某一道被认定为符合本裁定的 required gate，在独立复测时对其声明应拒绝的已知错误负样本返回成功，并使该负样本获得通过状态，则 A3 关于门禁能够通过负样本证明其失败能力的裁定被证伪。

复测必须使用该门禁实际适用的合并候选目标基；仅在不同 base SHA 上获得失败结果不能排除目标基错误。

### A4. Phase 3 退出改为可执行清单 / Phase 3 Exit as an Executable Checklist

#### Decision

适用于 ROADMAP 中 Phase 3 的退出判据及其所覆盖的组件、架构和产品能力：Phase 3 的退出必须由可观察、可执行、可复核的验收条件构成；“有界目的、归属、契约、开放问题”等文档属性只能作为必要的描述性条件，不得单独构成阶段退出的充分条件。此裁定不决定 Phase 5 的启动时点，也不将阶段退出自动等同于产品级运行时已经发布。

#### Rationale

1.5 显示仓库已经存在可串起全部 12 个 crate 的端到端测试。

1.6 显示 README 声明产品级运行时尚未启动，prototype/implementation 位于 Phase 5，而 Phase 3 的退出条件仍以组件文档属性为中心。

2.4 说明仅以文档属性定义退出条件，无法证明系统具备可执行能力，因此不能形成有效的阶段边界。

因此，Phase 3 退出必须能够通过实际行为或可重复验证结果判断，而不能只依赖组件说明是否完整。

#### Alternatives considered and rejected

**替代方案一：保留现有 Phase 3 退出判据，仅增加更多文档字段。**

否决理由：增加文档字段并未改变判据的可证伪性，反而可能进一步扩大记录负担。

**替代方案二：直接取消 Phase 3 退出条件。**

否决理由：取消退出条件会失去架构阶段与实现阶段之间的明确边界，不能解决产品实现长期缺少可验证入口的问题。

**替代方案三：把 Phase 3 退出等同于 Phase 5 产品发布。**

否决理由：阶段退出与产品发布是不同判断。前者证明阶段成果达到进入下一阶段的条件，后者还涉及产品运行时及其发布状态。

#### Consequences

本裁定采纳后，组件文档完整不能单独作为 Phase 3 已退出的证据。

必须放弃以“所有组件都有有界目的、归属、契约、开放问题”作为唯一充分退出条件的判断方式。

必须保留文档属性作为架构治理证据，但不能把它们替代端到端行为、接口契约验证或其它可执行验收结果。

既有 ROADMAP 阶段记录不因本裁定自动被追溯判为错误；其历史退出结论按当时有效的判据理解。

#### Falsifier

在本裁定适用范围内，若 Phase 3 被正式判定退出，而该退出判定仅依赖组件目的、归属、契约和开放问题等文档字段，没有任何可重复执行的行为验收或测试结果作为必要证据，则 A4 关于 Phase 3 退出必须具备可执行判据的裁定被证伪。

判定依据为实际退出记录及其引用的验收证据；仅存在端到端测试文件而没有将测试结果纳入退出判定，不构成满足条件。

### 7.5 证据完整性声明 / Evidence Integrity Statement

本记录区分三种证据：

1. **直接测量事实**：第 1 节列明的统计结果、文件关系和代码定位。
2. **因果诊断**：第 2 节根据直接测量事实形成的治理机制解释。
