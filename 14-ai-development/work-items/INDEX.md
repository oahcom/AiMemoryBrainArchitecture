# AI Work Items Index

This index is the entry point for all governed AI development tasks.

**Registration criterion (normative).** An AID directory or manifest existing on disk does not by itself require an INDEX row. Stage 0 is a pre-registration stage, not a major gate: while `gates.stage_0_registration.status` is `PENDING`, a registration field is `PENDING_*`, or the required formal-registration readback is incomplete, the work item is unregistered and no row is due. Once formal Stage 0 registration is complete and its readback is verified, an INDEX row MUST be present before R2 begins. An explicit, committed deferral in the manifest controls the deadline instead; in that case the row MUST be present before the deferred gate begins. Owner assignment is not an inclusion condition: when the row is due but no Owner is assigned, the Owner cell MUST say `NOT_ASSIGNED`. Status labels such as `PROPOSED` or `DISPATCHED` do not independently determine inclusion; the formal-registration evidence does. Two different things share this table and MUST NOT be read as one: a **registration row** is the row owed at the deadline above, and an **existence row** may be present before that deadline. An existence row records that the directory exists and repeats only the registration state the manifest itself declares. It is not a registration, confers no authorization and closes no gate, and it MUST NOT state a registration fact the manifest does not state — where the manifest carries no status field, the cell says so instead of inferring one. The membership check enforces one entry per work-item directory; a row that satisfies it is not thereby evidence of registration.

Two kinds of content in this table age differently, and the difference is normative. Binding facts — head SHAs, merge SHAs, run IDs, comment IDs, blob digests — are snapshots of a past observation: they stay true when the world moves, and they are never edited in place. Activity assertions — a `Status` cell saying a carrier is open or pending, a `Review` cell saying a review is pending — are claims about the present: they are false from the moment the carrier merges or closes. Therefore every `Status`, `Review` and `Acceptance` cell that names a carrier PR MUST be refreshed when that carrier merges or closes; a stale cell is a defect in this registry, not a historical record. The prior value is preserved by the diff of the correcting PR and itemised in the correcting work item's manifest, so the refresh loses no history; no cell is rewritten without an authorization that names it. A refresh records which outcome actually occurred, because the three are not interchangeable: a merged carrier records its merge SHA and merge time; a carrier closed without merging MUST NOT be described as merged and MUST keep the fact that it closed unmerged; a carrier reopened returns its cell to an active state rather than leaving the earlier terminal wording standing. A cell that asserts something about the work item as a whole rather than about a named carrier PR is outside this rule, and MUST state its own basis instead of borrowing the authority of a merge.

**Merge driver (normative for this table only).** `.gitattributes` declares `14-ai-development/work-items/INDEX.md merge=union`, so two concurrent registrations that each append a row merge without a conflict. Its contract is narrow, and a resolver who sees a duplicate-row failure is looking at one of three things it does not resolve:

- It guarantees that two **appends** merge without human intervention.
- It does **not** resolve an edit to a row present on both sides. Union keeps both variants, so one `AID` ends up on two rows with different cells.
- It does **not** preserve a deletion whose neighbouring line was changed on the other side. The deleted row comes back.
- All three silent outcomes end as the same `AID` on two lines, so `scripts/check_traceability.py --index-only` refuses them (`T-04 duplicate INDEX entry`). The message cannot tell you which of the three you have; the diff can. Pick a side by hand rather than re-running the merge.

That check is the reason the driver is safe. If it is ever removed or made advisory, the `.gitattributes` line goes in the same change.
