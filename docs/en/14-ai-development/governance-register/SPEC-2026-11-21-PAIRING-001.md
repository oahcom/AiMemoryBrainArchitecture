## 2. Policy requirement (Owner ruling A)

Normative Markdown permits two pairing forms, **equivalent, not a double obligation**:

| Form | Composition |
|---|---|
| S-side-by-side | same directory `X.md` + `X.zh-CN.md` |
| S-mirror | root source + `docs/en/X.md` + `docs/zh-CN/X.md` |

Constraints:

1. side-by-side must be a **same-directory, same-stem** exact pairing;
2. "any filename containing `.zh-CN`" must not substitute for it;
3. a single language side is not allowed;
4. existing exemptions (`EMBEDDED_BILINGUAL_SOURCES`, `PAIR_EXEMPT_PREFIXES`) continue to apply and **must not be widened**;
5. the two forms are alternatives, not cumulative requirements.

## 3.5 Supplementary measurement: why the existing `side_by_side_partner` cannot simply be reused

On a real clone, with only `14-ai-development/zzp.md` + `zzp.zh-CN.md` present (no `.en.md`, no mirror), calling the three resolvers directly:

```json
"14-ai-development/zzp.md":        {"side_by_side": null, "mirror": null, "counterpart_14": null}
"14-ai-development/zzp.zh-CN.md":  {"side_by_side": null, "mirror": null, "counterpart_14": null}
"14-ai-development/zzp.en.md":     {"side_by_side": "14-ai-development/zzp.zh-CN.md", ...}
"04-memory-compiler/zzq.md":       {"side_by_side": null, "mirror": null, "counterpart_14": null}
"04-memory-compiler/zzq.zh-CN.md": {"side_by_side": null, "mirror": null, "counterpart_14": null}
```

**Key observation: `X.md` and `X.zh-CN.md` do not recognise each other — both return `null`.**

The reason is in the `side_by_side_partner` branches:

```python
elif source.endswith(".md"):          # X.md looks only for X.en.md
    cand = stem + ".en.md"
elif source.endswith(".zh-CN.md"):    # X.zh-CN.md looks only for X.en.md
    cand = stem + ".en.md"
```

**Both branches look only for `.en.md` and never for each other.** So:

- `X.md` + `X.zh-CN.md` → neither side resolves;
- `X.md` + `X.en.md` → the `.en.md` side can resolve to `.zh-CN.md` (if present) or `.md`, but the `.md` side still looks only for `.en.md`, so it is **asymmetric**.

This explains why side-by-side never took effect in the gap scan: **not because `resolved_14` blocked it, but because this pair of filenames is not recognised as a pairing by any resolver.**

Therefore §4's proposal is not "widen an existing function's scope" but **add a symmetric same-directory resolver**.

## 4. Proposed implementation shape (for the reviewer to evaluate, not presupposed)

**Point: do not change `resolved_14`.** It is the **changed-path** resolver for `14-ai-development`, semantically different from the gap scan (§1). Reusing it inside the gap scan is exactly what made the first draft wrong.

Introduce an independent judgement serving the gap scan:

```python
def has_pairing(source: str) -> bool:
    """True if source has a same-directory same-stem side-by-side partner,
    or both docs/ mirrors exist."""
    english = REPO_ROOT / "docs" / "en" / source
    chinese = REPO_ROOT / "docs" / "zh-CN" / source
    if english.is_file() and chinese.is_file():
        return True
    return side_by_side_same_dir(source) is not None
```

`side_by_side_same_dir` must be distinct from the existing `side_by_side_partner`, because the latter:

- for `.md` looks only for `.en.md` (not `.zh-CN.md`);
- constrains on `ROOT` rather than the same directory.

The new judgement must satisfy:

| source suffix | looks for | constraint |
|---|---|---|
| `.md` | `<stem>.zh-CN.md` or `<stem>.en.md` | same directory |
| `.zh-CN.md` | `<stem>.md` or `<stem>.en.md` | same directory |
| `.en.md` | `<stem>.md` or `<stem>.zh-CN.md` | same directory |

**And the two sides must be each other's partner** (D-3's requirement), i.e. `partner(partner(x)) == x`.

### 4.1 Correction: two places must change, not one

§4's first draft said only "introduce an independent judgement serving the gap scan". **That is not enough** (§4.5.2c, measured).

A complete implementation of ruling A needs two call sites of the same resolver:

| Site | Domain | Current | Change |
|---|---|---|---|
| `current_bilingual_gaps()` | whole tree | accepts only `docs/en` + `docs/zh-CN` | non-null side-by-side means paired |
| `check_normative_pairing()` | diff | for the eight non-14 roots, unconditionally demands `docs/en` + `docs/zh-CN` in the same PR | non-null side-by-side becomes the sole partner |

The semantic difference between the two must be preserved:

- the gap scan asks "does this file have a partner in the tree";
- normative-change pairing asks "did this change also change the partner side".

Patch only the first and the PR still fails with "partner side not in this change" (`EXIT=1`); patch only the second and the trunk goes red because the new file becomes a gap (`EXIT=2`). **Both must change, and together with the baseline shrink in one commit.**

## 4.5 Uniqueness and symmetry rules (added at the Owner's request)

The Owner noted that `partner(partner(x)) == x` is necessary but insufficient to define all legal cases, and proposed:

> Allow legal two-file pairings; when more than two candidate files share a stem, refuse automatic pairing and report ambiguity unless the spec defines provable unambiguous three-file semantics.

**Adopted. The measurement behind it follows.**

### 4.5.1 Measured: three coexisting files make the existing resolver loop

With three files sharing a stem (`zz.md` / `zz.en.md` / `zz.zh-CN.md`), calling the existing resolvers directly:

```json
"04-memory-compiler/zz.md":        {"sbs": "04-memory-compiler/zz.en.md"}
"04-memory-compiler/zz.en.md":     {"sbs": "04-memory-compiler/zz.zh-CN.md"}
"04-memory-compiler/zz.zh-CN.md":  {"sbs": "04-memory-compiler/zz.en.md"}
```

Identical shape under `14-ai-development`.

Three consequences:

1. **asymmetric**: `zz.md → zz.en.md`, but `zz.en.md → zz.zh-CN.md`, so `partner(partner(zz.md)) = zz.zh-CN.md ≠ zz.md`;
2. **no direct pairing between `.md` and `.zh-CN.md`**: `zz.zh-CN.md` looks for `.en.md`, not `.md`;
3. **`.en.md` is the only file referenced from both sides**, becoming a de facto hub whose two "partners" do not know each other.

Copying that logic to implement ruling A would make the `X.md` + `X.zh-CN.md` pairing depend on whether an unrelated third file, `.en.md`, exists. **That coupling is unacceptable.**

### 4.5.2 Rules

Following the Owner's proposal, the spec adopts **strict binary pairing, ambiguity refused**:

#### R-1 only two legal forms are recognised

| Form | Composition | Note |
|---|---|---|
| P1 | `X.md` + `X.zh-CN.md` | same directory, same stem |
| P2 | `X.md` + `X.en.md` | same directory, same stem |
| P3 | `X.md` + `docs/en/X.md` + `docs/zh-CN/X.md` | three-part mirror |

**The three-file side-by-side form (`X.md` + `X.en.md` + `X.zh-CN.md`) is not recognised.**

#### R-2 uniqueness

For any source the partner must be **unique**:

```
candidates(source) = { existing among .md / .en.md / .zh-CN.md in the same dir with the same stem } - {source}
```

- `|candidates| == 1` → pairing holds, and `partner(partner(source)) == source` must be true;
- `|candidates| == 0` → no side-by-side pairing; fall through to the P3 mirror;
- `|candidates| >= 2` → **ambiguous: judged a gap, and reported as `AMBIGUOUS_PAIRING`**.

#### R-3 no priority rules to mask ambiguity

"Prefer `.zh-CN.md`" and similar rules are forbidden: a priority rule lets the same tree **silently change** an existing pairing when one file is added, and an incremental change does not trigger a full re-check.

#### R-4 how ambiguity is reported

Ambiguity must not appear merely as "a gap", or it cannot be distinguished from "genuinely missing a partner":

```
::error::Ambiguous bilingual pairing for <source>: candidates <a>, <b>
```

The gap set still contains that source (conservative: ambiguity does not pass).

#### R-5 precedence of P3 over P1/P2

If a source satisfies both P1 and P3:

- it is **legal** (P3 is the stronger form, both `docs/` sides present);
- **no ambiguity is reported**, since P3 does not depend on side-by-side candidate uniqueness;
- but the report carries `PAIRED_BY_MIRROR_AND_SIDE_BY_SIDE` for the reviewer to check whether the prose differs.

#### R-6 inventory compatibility

Existing files already in three-file form would be judged ambiguous under R-2 and counted as gaps.

**That is intentional**: it exposes inventory ambiguity rather than silently accepting it. To avoid manufacturing a large number of new gaps at once, the implementation must:

1. first count the inventory files matching that form;
2. if the count is greater than zero, register those files explicitly in `EMBEDDED_BILINGUAL_SOURCES` or the baseline, and list them separately as an "inventory ambiguity list";
3. not relax R-2 in order to reduce the gap count.

### 8.9 Note on the measurement harness itself

An earlier round of this work concluded that PR #470 had written a GitHub API JSON response into `scripts/bilingual-baseline.txt`. **That conclusion was wrong and is withdrawn.** The cause was the harness: `GET /git/blobs/{sha}` returns `{"sha":...,"content":"<base64>","encoding":"base64"}`, and the fetch helper wrote that wrapper to disk verbatim, so every "downloaded" file was JSON. With correct base64 decoding, #470's baseline is a legitimate 80-entry plain-text file.

Every measurement from §8.1 onward was re-run with the corrected harness. Readers reproducing this work must decode the base64 payload, not store the wrapper.
