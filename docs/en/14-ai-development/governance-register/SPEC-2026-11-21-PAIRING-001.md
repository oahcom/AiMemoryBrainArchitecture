## 2. Policy requirement (Owner ruling A)

Normative Markdown may use either shape, and **the two are equivalent, not a double obligation**:

| Shape | Composition |
|---|---|
| S-side-by-side | same directory `X.md` + `X.zh-CN.md` |
| S-mirror | root prose + `docs/en/X.md` + `docs/zh-CN/X.md` |

Constraints:

1. side-by-side must be an **exact same-directory, same-stem** pairing;
2. a file that merely contains `.zh-CN` does not qualify;
3. one-sided language coverage is not allowed;
4. existing exemptions (`EMBEDDED_BILINGUAL_SOURCES`, `PAIR_EXEMPT_PREFIXES`) keep applying and **must not be widened**;
5. the two shapes are alternatives, not cumulative requirements.

## 3.5 Additional measurement: why the existing side_by_side_partner cannot be reused

On a real clone with only `14-ai-development/zzp.md` + `zzp.zh-CN.md` present (no `.en.md`, no mirrors), calling the three resolvers directly:

```json
"14-ai-development/zzp.md":        {"side_by_side": null, "mirror": null, "counterpart_14": null}
"14-ai-development/zzp.zh-CN.md":  {"side_by_side": null, "mirror": null, "counterpart_14": null}
"14-ai-development/zzp.en.md":     {"side_by_side": "14-ai-development/zzp.zh-CN.md", ...}
"04-memory-compiler/zzq.md":       {"side_by_side": null, "mirror": null, "counterpart_14": null}
"04-memory-compiler/zzq.zh-CN.md": {"side_by_side": null, "mirror": null, "counterpart_14": null}
```

**Key observation: `X.md` and `X.zh-CN.md` do not recognise each other — both return `null`.**

The cause is in `side_by_side_partner`:

```python
elif source.endswith(".md"):          # X.md only looks for X.en.md
    cand = stem + ".en.md"
elif source.endswith(".zh-CN.md"):    # X.zh-CN.md only looks for X.en.md
    cand = stem + ".en.md"
```

**Both branches look only for `.en.md` and never for each other.** So:

- `X.md` + `X.zh-CN.md` -> neither resolves;
- `X.md` + `X.en.md` -> the `.en.md` side can resolve to `.zh-CN.md` or `.md` if present, but the `.md` side still looks only for `.en.md`, so it is **asymmetric**.

This explains why side-by-side never worked in the gap scan: **it is not blocked by `resolved_14`; the filename pair is simply not recognised as a pair by any resolver.**

So the recommendation in section 4 is not "widen the existing function's scope" but **add a new symmetric same-directory resolver**.

## 4. Suggested implementation shape (for the reviewer to evaluate, not prescribed)

**Do not change `resolved_14`.** It is `14-ai-development`'s **changed-path** resolver and its semantics differ from the gap scan (section 1). Reusing it in the gap scan is precisely what made the first draft's judgement wrong.

Introduce a separate predicate serving only the gap scan:

```python
def has_pairing(source: str) -> bool:
    """True if source has a same-directory same-stem side-by-side partner,
    or both docs/ mirrors exist."""
    english = REPO_ROOT / "docs" / "en" / source
    chinese = REPO_ROOT / "docs" / "zh-CN" / source
    if english.is_file() and chinese.is_file():
        return True
    return side_by_side_same_dir(source) is not None
```

`side_by_side_same_dir` must be distinct from the existing `side_by_side_partner`, because the latter only looks for `.en.md` from `.md` and is not directory-constrained the way this needs.

Required resolution table:

| source suffix | look for | constraint |
|---|---|---|
| `.md` | `<stem>.zh-CN.md` or `<stem>.en.md` | same directory |
| `.zh-CN.md` | `<stem>.md` or `<stem>.en.md` | same directory |
| `.en.md` | `<stem>.md` or `<stem>.zh-CN.md` | same directory |

And the two sides must be mutual, i.e. `partner(partner(x)) == x` (D-3's requirement).
