# EX-20261123-01 — §5 independent review unavailable (retrospective)

**This is the first exception record in this repository.** Before it there were 675 merged PRs and 0 exception records.

`PR-GOVERNANCE-001` §5, final sentence: **"Record exceptions explicitly; do not silently waive the requirement."** This record is what that sentence asks for. It waives nothing, changes no PR's disposition, and converts no `HOLD` into `MERGE`.

The field set follows two documents. `AI-EXEC-001` §6 (**ADOPTED**, PR #256 merge `48a55649`) supplies six mandatory items. `AI-EXEC-INDEPENDENCE-RULING-001` RULING-06 (**PROPOSED**, not adopted) supplies a seventeen-field superset. This record fills the superset, so that adopting that ruling later requires no rewrite.

So the missing control was recorded as "a GitHub review identity distinct from the author", the missing resource as "a second GitHub identity holding `write`", the reason as "the only writable identity is the only authoring identity, so §5's approval cannot exist under the current configuration", closure (a) as "the administrator grants a second identity `write`", and the disclosure as "no second actor". That criterion was amended on 2026-11-24 (`GOV-REV-2026-11-24-INDEPENDENCE-IS-SESSION-LEVEL-036`, PR #935, commit `2eb4e352`). The retired sentence was "when the author and the reviewer use the same GitHub identity, that is not an independent review". Live §5 (`14-ai-development/PR-GOVERNANCE-001.md`) provides: independence is a property of the reviewing **session**, not of the GitHub account that carries it; several sessions may share one GitHub identity; only a session that neither wrote nor implemented the change, and whose conclusion comes from the artifact rather than from the author's account of it, is an independent review.
>
> So the **reason** given in those five rows is void; the **outcome** of this record need not be. If the exception still stands, its reason can only be "**no independent session was ever run**", not "no second account exists". Whatever rested on "structurally unavailable" or "§5's approval cannot exist under the current configuration" is wrong *as a reason*, even though `HOLD` is preserved unchanged — the two must be stated separately, not swapped silently while the original reason is left standing as if correct. "No second actor" is true at the account layer; at the session layer it does not rule out a separate session under the same identity being an independent review.
>

The correct closure condition is "a session that neither wrote nor implemented the change performs the review and records an approval that counts", which one GitHub identity can satisfy; if that review never happened, the other route remains amendment of §5 in a daily governance window (original (b)). Whether original (a) is kept as an optional extra is for the governance window, not this note; and this note does not claim an independent review occurred — the original `NOT_ASSIGNED` and 0 `APPROVED` are not rewritten here.

## 1. Two readings of the count, and why both point at one action

RULING-06 says "register one per distinct blocked Work Item/PR plus missing mandatory control/resource", and also says "the same control and a continuous blocked interval for one PR counts once". The two pull against each other on "continuous interval":

| Reading | Count here | Cap | Result |
|---|---|---|---|
| **Continuous blocked interval** × missing control | **1** | ≤ 2 / iteration | within quota |
| **Distinct PR** × missing control | **675** | ≤ 2 / iteration | far over quota |

Both readings must be recorded, because choosing one changes the conclusion. This record does not pick: it writes down both numbers and leaves the choice to the daily governance window.

But under one reading the conclusion does not depend on the choice. If the interval reading is taken, the record must also state that **the interval is still open** — it did not end on 2026-11-23, because the second identity still does not exist. An exception counted as one and still open, and an exception counted as 675 and over quota, point at the same act: **open the window**.

> **Added 2026-11-25 (citation currency).** The paragraph above ties "the interval is still open" to "the second identity still does not exist". Under §5 as amended on 2026-11-24 (`GOV-REV-2026-11-24-INDEPENDENCE-IS-SESSION-LEVEL-036`, PR #935) the interval is open or closed by **whether an independent session was run**, not by whether a second account exists. The conclusion of that paragraph is unaffected (interval open → open the window): the record's own facts — 0 `APPROVED` across 675 PRs, and review never requested — point, under the new criterion, at the same thing, "no independent session was ever run".

## 2. What this record does not do

- It does not re-review any merged PR. History is not rewritten, and no past merge is retroactively marked compliant.
- It does not claim §5 was satisfied. It never was; this record is the record of that fact.
- It does not move any merge in this repository from `HOLD` to `MERGE`. RULING-05's boundary, verbatim: "Exception alone never changes HOLD to MERGE."
- It does not represent Owner approval. The account layer cannot distinguish an owner-proxy session's decision from an Owner's, which `GOV-NC-2026-11-21-ZERO-REVIEW-GATE-008` §10.3 already recorded; this record claims nothing stronger.

## 3. Why now

This record is late, and the reason it is late is itself worth one line: **in a repository that never records exceptions, the quota can never overflow.** `AI-EXEC-001` §6's clause — "exceeding the quota in 2 consecutive iterations triggers a daily governance window for rule revision" — takes the exception count as its input. At a count of zero the clause cannot fire, so the standard loses its own lawful route to amend itself. Recording exceptions is not paperwork; it is connecting that route.

Ruling: `OWNER-DECISION-REVIEW-INDEPENDENCE-001` (`14-ai-development/adr/`). **That ruling's §3, §4, §6, §7 and §8 were partly withdrawn on 2026-11-25 by its §9 erratum: one of the three remedies was executable, and has been executed. This exception record does not depend on the ruling standing — it depends on §5's sentence "record exceptions explicitly", which has not changed.**
