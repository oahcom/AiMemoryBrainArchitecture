# 架构文档中英双语规范

- 规范 ID：DOC-STD-001
- 版本：1.0
- 状态：PROPOSED — 等待 Architecture Governance 批准
- 适用范围：本仓库中的所有架构、领域、协议、安全、工程、决策、审查和运维设计文档。

## 1. 规范性要求

每一份新建或发生实质性修改的架构/设计文档，**MUST** 在同一个变更集中同时提供英文版和简体中文版。任何一种语言都不是可选项。两个版本必须具有相同的 Document ID、语义版本、状态、Owner、Source Revision、Decision State、Issue Reference 和规范效力。

只有在两个版本均已更新、相互链接并完成语义一致性检查后，该变更才算文档交付完整。缺失翻译或存在实质性过时翻译属于审查发现；如果变更涉及 Contract、Invariant、安全规则、数据模型、协议、决策或实现要求，则阻止文档验收。

## 2. 规范路径

- 英文：`docs/en/<domain>/<document-name>.md`
- 简体中文：`docs/zh-CN/<domain>/<document-name>.md`
- 导航入口：`docs/README.md` 及其中文版 `docs/zh-CN/README.md`。

现有 Owner 源文档和审查报告仍保留在既有路径。双语文档集是面向读者的关联版本，不会静默替换或修改 Owner 分支中的原始工件。

## 3. 语言与术语

- 英文是跨 Owner 共享的术语基线，适用于标识符、协议字段、代码符号、状态名称、枚举值、错误码和 Schema Name。
- 简体中文必须是完整技术版本，不是摘要。所有要求、限定条件、表格、示例、公式、错误名称、开放问题和验收标准都必须保留。
- 当翻译可能改变互操作语义时，规范关键词（MUST、MUST NOT、SHOULD、MAY）、标识符、代码符号、状态名称和准确字段名必须保持原样。
- 建立项目术语表管理领域术语。解释性文字应翻译，但不得翻译代码标识符或 Wire Value。
- 避免含混直译；术语一经定义，全文保持一致。

## 4. 必需文档元数据

每个语言版本 **MUST** 声明：Document ID、标题、版本、状态（适用时使用 DECIDED/CANDIDATE/OPEN/ADR-BLOCKED/IMPLEMENTED/VERIFIED）、Owner、Source Path 和准确 Source Commit/Blob、对应语言版本链接、相关 ADR/Issue ID、最后审查的 Revision。

没有证据时，不得声称已经实现、执行测试、完成性能测量、通过外部审查或获得治理批准。必须区分设计决议、候选提案、开放问题、实现状态和已验证行为。

## 5. 易读性与结构

在适用时采用稳定目录：
1. 目的与目标读者
2. 范围与非职责
3. 术语与领域模型
4. 职责和所有权边界
5. 架构/组件及依赖
6. 数据模型和状态模型
7. 接口/契约
8. 不变量与安全约束
9. 正常流程与生命周期
10. 故障恢复与并发
11. 性能/资源假设及验证计划
12. 可观测性
13. 验收/一致性测试
14. 开放决策、依赖和变更历史

每份文档开头先给出简明白话摘要和明确状态。先解释组件为什么存在，再介绍字段细节。规范性规则必须与设计理由、示例分开。缩写首次出现时给出全称。比较和所有权矩阵优先使用表格；只有在能够解释顺序或并发关系时才使用时序图。避免未经解释的缩写链和过长段落。

## 6. 双语一致性检查清单

审查/合并前必须核验：
- 章节和要求覆盖范围一致；
- MUST/MUST NOT/SHOULD/MAY 的规范力度一致；
- 状态转换、字段名、类型、单位和枚举值一致；
- Owner、依赖和接口边界一致；
- 故障模式、重试/幂等和恢复行为一致；
- 安全、隐私和 Forget 语义一致；
- 示例、表格、公式和验收测试一致；
- OPEN/DECIDED/ADR-BLOCKED 状态一致；
- 仓库内链接有效，且两个版本指向相同 Source Revision。

翻译可以改善解释，但 **MUST NOT** 增加、削弱或删除规范性要求。如果源文档存在歧义或矛盾，必须在两个版本中记录该问题；不得在翻译时静默裁决。

## 7. 变更流程

1. 同时编写或修改英文版和中文版。
2. 更新元数据和 Source Revision 引用。
3. 必要时更新导航索引和术语表。
4. 执行链接/路径检查和双语语义一致性审查。
5. 由 Owner Architect 确认技术含义；安全/协议/数据模型变更还应由独立 Reviewer 审查。
6. 在一个完整、连贯的变更中提交两个版本和索引更新。
7. 重新读取已提交文件，验证准确路径、Commit 和 Blob Identity。
8. 完成以上步骤后，才能报告文档工作已完成。

## 8. 例外

临时例外必须由 Architecture Governance 明确批准，并设置有效期限，同时记录 Owner、理由、受影响文档、风险和整改日期。除此之外，只有英文版或只有中文版都不符合规范。

## 9. 验收

本规范自身在 Architecture Governance 批准前仍为 PROPOSED。获批后，双语完整性成为仓库级审查 Gate。本规范不代表任何文档的技术内容已获批准，不关闭 ADR，也不构成实现证据。
